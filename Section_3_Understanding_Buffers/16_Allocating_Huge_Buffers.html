📝 Having Fun with Buffers – Study Notes

🖥️ Running a Virtual Machine (VM)

  • 🔄We run Ubuntu Linux inside Parallels on our Mac/Windows.
  • 💡Treat the VM like a separate computer with 2 CPU cores + 2 GB RAM.
  • 🖱️Open “System Monitor” (Linux) to watch CPU & memory usage.
  • 🌐In real life, many servers are VMs with 1 – 2 GB RAM and a couple of CPU cores.

✍️ Writing huge-allocation.js

  • 📁Create a new file: 
    touch huge-allocation.js
  • 🕹️Open it in your editor:
    • code huge-allocation.js
  • 🔌Require the Buffer module at the top: 
    const Buffer = require('buffer').Buffer;

📦 Allocating a Large Buffer

  • 🔢We try to reserve a big chunk of memory for our Node app:
    • const bigBuf = Buffer.alloc(1e9);  
// 1 × 10⁹ bytes = 1 GB
  • ⚠️If your VM has only 2 GB RAM, 1 GB buffer uses half the memory.
  • 💾Each time you do Buffer.alloc(n), Node “locks” n bytes in RAM for itself.

⚙️ Filling the Buffer (Slow Way)

  • 🔄Inside huge-allocation.js, add a loop to fill every byte:
    • setInterval(() => {
  for (let i = 0; i < bigBuf.length; i++) {
    bigBuf[i] = 0x22;
  }
}, 5000);
  • ⏳This loop runs every 5 seconds, setting each byte to 0x22.
  • ⚙️bigBuf.length returns the buffer size in bytes (1 000 000 000).

📊 Watching RAM in “System Monitor”

  • ⚙️Run the script: 
    node huge-allocation.js
  • 👀In System Monitor → “Processes,” find the “node” process.
  • 📈Watch “Memory” column: It jumps to ~1 GB once Buffer.alloc(1e9) runs.
  • 💜The VM’s total RAM bar turns mostly purple (≈ 95 % used).

💥 Crash When Buffer Too Large

  • ⚠️Trying to allocate ≥ 2 GB in a 2 GB VM makes the OS run out of memory and crash.
  • 🛑Example: Buffer.alloc(2e9) (2 × 10⁹ bytes) → VM freezes, then crashes.
  • 📦Always be careful: allocating more RAM than available kills your system!

🔍 Trying 500 MB Instead

  • ✂️Change allocation to 0.5 × 10⁹ bytes (500 MB): 
    const bigBuf = Buffer.alloc(5e8);  
// 5 × 10⁸ bytes = 500 MB
  • 👀Run node huge-allocation.js again.
  • 📊System Monitor shows “node” using ~500 MB RAM, and the VM bar → ~50 % full.
  • ⚙️Every 5 seconds, the loop or fill updates the buffer. CPU usage “spikes” on each fill.

⚡ Using buffer.fill() (Faster)

  • 🛠️Instead of looping byte-by-byte, use fill: 
    setInterval(() => {
  bigBuf.fill(0x22);
}, 5000);
  • 🚀fill() is 2–3× faster than a manual loop, because it’s optimized in Node.js.
  • 📈RAM usage remains the same (~500 MB), but CPU time to fill is lower.

🔢 Maximum Default Buffer Size

  • 📋Check Node.js’s max buffer length: 
    const { constants } = require('buffer');  
console.log(constants.MAX_LENGTH); // ~4294967295
  • ⚙️By default, Node.js allows up to ~4 GB buffers (2³² – 1 bytes).
  • 💾In practice, you must have enough free RAM (plus OS overhead) to allocate that much.
  • ⚠️Allocating a buffer close to your total RAM leads to crashes—so watch your limits!

✅ Key Takeaways

  • 🧠Buffers allocate real RAM; Buffer.alloc(n) “reserves” n bytes.
  • 📊Use System Monitor (Linux) or Task Manager (Windows) to see how much memory Node uses.
  • ⚡buffer.fill(value) is faster than a manual loop for filling large buffers.
  • 💥Do not allocate more bytes than your machine has—your OS will crash if you exceed available RAM.
  • 🔢Default maximum buffer size in Node is ~4 GB, but actual safe limit = (total RAM – OS & other apps).
